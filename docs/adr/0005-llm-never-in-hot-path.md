# ADR-0005: 性能红线 — LLM 永不进热路径

- 日期：2026-08-11
- 状态：已接受

## 背景

v2 引入多项"双保险"机制（类型推断、冲突检测、敏感补扫、综合检索、衰减计算）。用户担忧：多机制叠加是否拖慢记忆系统日常操作。

## 决策

设定性能红线：**同步热路径（用户每次操作触发的路径）= 零 LLM、零网络，仅本地正则/SQL/规则（µs~ms 级）**。

所有需要 LLM 的操作必须落在以下路径之一：
- **后台批处理**：consolidate 周整理（LLM 补扫、语义冲突检测、类型复查、衰减计算、SKILL 草稿生成）——每周一次，异步，用户无感知；
- **冷路径（用户主动触发）**：`search --synthesize`（LLM 综合回答）——用户请求 LLM 输出，等待可接受；
- **提交时**：pre-commit 全量扫描（git 提交节奏内）。

具体约束：
- 写入时冲突检测**只做本地相似度**（标题/标签/关键词重叠），语义检测留给 consolidate。
- 写入时敏感拦截只用正则（Block/Mark 两级），LLM 补扫留给 consolidate。
- 性能验收标准：热路径写入 ≤50ms（实测目标 ~10ms via daemon）。

## 备选方案

- 写入时同步调 LLM 做语义冲突/类型精判：精确但热路径秒级延迟，vibe coding 连贯性被破坏（v1 的 1.3s 已证明不可接受）。
- 全部机制只留后台：热路径永远快，但写入时失去冲突提示与拦截能力。

## 后果

- 热路径与机制数量解耦：无论加多少"智能"，日常操作感知不变。
- 代价：语义级判断（冲突、敏感、分类）存在最长一周的延迟窗口，靠三层防线与冲突卡兜底。
- 实测基准：search ~100ms（其中 60-80ms 为 Python 启动，daemon 化后可归零）；万条级 FTS 查询仍为 ms 级。
